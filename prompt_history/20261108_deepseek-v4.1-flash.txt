# 結論: 実現可能（ただし設計上の分岐が1つ）

| 要件 | 判定 | 根拠・方式 |
|---|---|---|
| ① ブラウザ完結でWEB公開 | ◎ | `comment-channel` と同じ **S3 + CloudFront の静的配信のみ**。画像をアップロードしないのでバックエンド不要 |
| ② profile `okamo` / 東京 | ◎ | `okamo` = account `123456789012`（`comment-channel` のテンプレートと同一）。AWS CLI 2.34.7 / SAM 1.163.0 / Node 24 導入済み |
| ③ Gemini 3.5 Flash-Lite | ◎ | 現行モデル `gemini-3.5-flash-lite`（$0.30/$2.50 per 1M tokens）。画像 → 座標検出（`box_2d`、0–1000正規化）に対応。ブラウザから直接呼べる |
| ④ Gemini以外に送らない | ○ | 静的配信 + **BYOK（利用者自身のAPIキー）** + 全アセット自前ホスト + CSP で技術的に担保可能。ただし後述の注意あり |
| ⑥ 複数D&D / マスク訂正 / 一括DL | ◎ | Canvas系ライブラリ + クライアント側ZIP。**HEICだけ△**（ブラウザ非対応） |
| ローカルLLM(Ollama) | △ | 公開サイトから `localhost` を叩くのは一般公開には不向き。代わりに **ブラウザ内WASMモデル** が本命 |

**コスト概算**: Gemini は1枚あたり約0.05円（1024pxに縮小して送る場合）。100枚でも数円。ホスティングは CloudFront/S3 で月数十円〜。

# 推奨アーキテクチャ

```mermaid
flowchart LR
  U[ブラウザ] -->|GET 静的ファイル| CF[CloudFront]
  CF --> S3[(S3 ap-northeast-1)]
  U -->|画像＋プロンプト<br/>APIキーはブラウザ内| G[Gemini API<br/>gemini-3.5-flash-lite]
  subgraph ブラウザ内で完結
    U --- W[WASM: 顔検出/OCR]
    U --- C[Canvas: マスク編集]
    U --- Z[ZIP生成・一括DL]
  end
```

- **Lambda / API Gateway は不要**（＝画像がokamoさんのサーバを通らない構造そのものが④の保証になる）
- 資産（JS/CSS/WASM/言語データ/フォント）は**全部S3から配信**。CDN・解析・Sentry・外部フォント禁止
- `Content-Security-Policy: connect-src 'self' https://generativelanguage.googleapis.com` で「Gemini以外に送れない」ことを機械的に強制

### 検出の設計（精度の要）
1. 元画像を**長辺1024〜1536pxに縮小**してGeminiへ送る（速度・コスト・転送量の削減）
2. 返ってくる `box_2d`（`[ymin, xmin, ymax, xmax]` を1000で正規化）を**元解像度へ逆変換**
3. さらに**ブラウザ内WASM（MediaPipe等）で顔を一次検出**し、Gemini結果とマージ
4. 座標は必ず**ユーザーが矩形/楕円/多角形で訂正**（源さんの記事と同じ「AI＋人手」の思想）

# 懸念点（重要度順）

| # | 懸念 | 内容・対策 |
|---|---|---|
| **1** | **プライバシーのパラドックス**（最重要） | 目的が「APIキーや顔を隠す」なのに、**隠す前の画像をGeminiに送る**ことになる。対策: デフォルトはローカル検出、Geminiは**オプトイン**。あるいは「先に手動で隠す→残りをGeminiで補完」 |
| **2** | APIキーの扱い | 一般公開でokamoさんのキーを共有すると**悪用・課金爆発**。またプロキシを置くと画像がAWSを通り**④違反**。→ BYOK一択が筋（キーはメモリ保持、HTTPリファラ制限＋クォータ上限を推奨） |
| **3** | 「サーバに送らない」の定義 | CloudFront/S3のアクセスログには**IP・UA等のメタデータ**が残る（画像は残らない）。アクセスログ無効化 or 保持期間明示を推奨 |
| **4** | Geminiのデータ利用条件 | 無料枠は学習利用され得る。**有料枠**の利用を推奨し、READMEに明記 |
| **5** | HEIC / TIFF | iPhone写真のHEICはChrome/Firefoxで開けない。HEIC対応にはWASM変換（+1〜2MB）。**必須か要確認** |
| **6** | 大量・高解像度のメモリ | 20枚×48MPを一括処理するとタブ落ち。**1枚ずつ逐次処理**＋`createImageBitmap`/OffscreenCanvas/Worker |
| **7** | 検出漏れ前提のUI | 「この写真は未確認」状態を管理し、**確認済みチェック**を付けないとDLさせない、等の安全弁 |
| **8** | EXIF（GPS）残留 | マスクしても位置情報が残る。**書き出し時にEXIF/XMP削除**を標準に（大きな付加価値） |
| **9** | ドメイン/証明書 | `comment-channel.okamomedia.tokyo` の証明書は流用不可（ワイルドカード無し）。**新規ACM証明書（us-east-1）が必要**。さらに**このアカウントにRoute53ホストゾーンが見当たらない**ため、DNSの管理場所を確認したい |
| **10** | Ollama | 公開HTTPSサイトから `http://localhost:11434` は、CORS設定・Private Network Access・ブラウザ差・利用者の導入ハードルがあり一般公開向きでない。**個人利用限定なら可**。「ローカル」の本命は**ブラウザ内WASM**（源さんの“小さなモデル”の話とも合致） |
| 11 | 名称・意匠 | 「フォト消しプライバシー」の名称/UIの模倣は避ける。源さんへの**リスペクト明記**と「AI検出は100%でない」免責を入れる |

## 1. なぜ Gemini の枠が広かったか

Gemini は汎用の視覚言語モデルで、座標は「おおよそ」で返します。さらに私のプロンプトが「少し余白を含めた矩形」と指示していたため、髪・背景まで含む大きな箱になっていました。

## 2. 改善内容（2点）

**(a) プロンプトを厳密化**
- 顔は「眉からあごまで、耳を含む顔の輪郭」にぴったり
- 髪・帽子・首・背景は含めない
- 余白は最小限、対象より明らかに大きい箱は返さない

**(b) ハイブリッド補正（本命）**
Gemini の顔の箱を、**ブラウザ内の顔検出のタイトな箱で置き換える**ようにしました。

- 検出パネルに **「顔の枠をブラウザ検出で補正」**（初期ON）を追加
- Gemini の箱とローカル顔検出の箱が重なっていれば、ローカルの箱を採用
- Gemini が見落とした顔も、ローカル検出で拾えるので**検出漏れも減る**
- 顔モデルが読めない環境では自動で Gemini の結果をそのまま使用（安全にフォールバック）

> 初回だけ顔モデル（WASM 約15MB＋モデル3.6MB）を読み込みます。2回目以降はキャッシュされ、通信は発生しません。

## 3. ブラウザ版の技術

「すごいね」の正体は、Google の OSS **MediaPipe Tasks Vision** です。

| 要素 | 内容 |
|---|---|
| 検出器 | BlazeFace（軽量な単発物体検出モデル、モバイル/エッジ向け） |
| ランドマーク | **478点の3D顔メッシュ**（目・鼻・口・輪郭） |
| 実行環境 | **WebAssembly**（CPUは XNNPACK、対応環境では WebGL/GPU delegate） |
| モデルサイズ | 約3.6MB（＋WASM約15MB）。すべて当サイトから配信 |
| 通信 | **ゼロ**。端末内で完結 |

478点の座標の最小・最大を取って矩形にしているので、髪を含まない「顔の輪郭」に沿った箱になります。源さんが書いていた「小さなモデルを組み合わせて実用的な仕組みを作る」に近い構成です。

（余談: MediaPipe は内部でテレメトリを送ろうとしますが、当サイトの CSP が `odml.pa.googleapis.com` への通信をブロックしているのを実機で確認済みです。）
