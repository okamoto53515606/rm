# rm — 競合分析と SEO / LLMO 方針

最終更新: 2026-11-14

---

## 1. 前提

### この文書が前提にしていること

| 項目 | 前提 |
|---|---|
| 目的 | 収益化ではなく「使ってもらうこと」と「okamo の技術的な信頼形成」 |
| 提供形態 | 無料・MIT・Web ツール（https://rm.okamomedia.tokyo/）。バックエンドなし |
| 収益 | なし。広告・課金・アフィリエイトを置かない |
| 計測 | アクセス解析なし（Cookie・外部スクリプトなし）を**売り**にしている。Search Console は `okamomedia.tokyo` のルートで登録済み・運用中 |
| 対応環境 | PC 専用と明示（`README`・`index.html` の `description`・ヘッダーのバッジ） |
| 配信 | S3（ap-northeast-1）+ CloudFront。SPA 1 ページ + `terms.html` / `privacy.html` |
| 競合の主戦場 | 日本語の「モザイク／ぼかし」検索。Canva・モザル・バナー工房・Mozaiku が上位 |

### 前提から導かれる制約

- アクセス解析を足すと差別化の根拠が崩れる → 計測は **Search Console（DNS 認証）+ CloudFront アクセスログ**で行う。
- 1 ページしかない → **検索クエリを 1 つしか取りに行けない**。これが最大の伸びしろ。
- 名前が `rm` → Unix コマンドと衝突し、**指名検索・AI 検索でエンティティ解決できない**。

## 2. 競合分析

### 2-1. 直接競合（同じ課題を解くツール）

| ツール | 形態 | 価格 | 自動検出 | 処理場所 | スマホ | 強み | 穴（rm が入れる余地） |
|---|---|---|---|---|---|---|---|
| **フォト消しプライバシー**（ソースネクスト） | デスクトップアプリ Win/mac | 3,980 円 | 顔・車/バイクのナンバー・地名を含む看板テキスト・QR | ローカル（認証時のみ通信） | × | ブランド、スタンプ、背景一括ぼかし、前後比較（最大 8 倍）、台形/円形、複数枚一括、元画像を残す保存、TIFF | 有料・インストール要・PC のみ。**API キー / ターミナル / パス は対象外** |
| **モザル**（shin-yu.net） | Web | 無料 | なし（手動） | ブラウザ | ○ | 完全無料・登録不要・多言語・HEIC・JPEG 品質 100・更新履歴・FAQ・構造化データ完備・姉妹ツール（追尾モザル） | 自動検出がない |
| **Mozaiku**（mozaiku.app） | Web | 無料 | 顔 + ナンバー | ブラウザ | ○ | 自動検出、複数枚を連続処理、ブラシ/四角/楕円、貼り付け | 文字（API キー等）非対応。EXIF の訴求が弱い |
| **バナー工房** | Web | 無料 | なし | **サーバー**（90 分で削除） | ○ | 老舗・被リンク・「定番」の評価 | アップロード型。プライバシー訴求で逆転できる |
| **Canva** | Web/アプリ | 無料〜 | なし | クラウド | ○ | 巨大ブランド・デザイン統合 | ログイン必須・アップロード必須 |
| **facepixelizer** | Web | 無料 | 顔 | ブラウザ | ○ | 顔自動 + EXIF 削除 | 日本語 UI なし・ナンバーなし |
| **digtools** | Web | 無料 | 顔（YuNet 212KB） | ブラウザ | ○ | 軽量・説明が丁寧 | ナンバーなし・文字なし |
| **rm** | Web | 無料（MIT） | 顔 + ナンバー + **機密文字列**（API キー・トークン・.env・メール・IP・パス・端末プロンプト） | ブラウザ | × | 開発者のスクショに唯一最適化、OSS で検証可能、EXIF 削除、ZIP 一括、CSP で送信を技術的に遮断 | モバイル非対応、認知ゼロ、被リンク実質ゼロ、ページ 1 枚 |

### 2-2. 間接競合（「ツール」と呼ばれない代替手段）

| 代替手段 | 実際の使われ方 | rm との関係 |
|---|---|---|
| OS 標準（macOS マークアップ / Windows 切り取り・ペイント） | 1 枚だけなら最速。多くの人がここで済ませる | 「複数枚」「検出漏れ防止」「EXIF 削除」で上回る |
| `screenshot-masker`（CLI・OSS） | 開発者がターミナルで一括処理 | **思想が近い**。rm は「インストール不要・GUI・ブラウザ」で差別化 |
| Photopea / GIMP | レイヤーで黒塗り | 学習コストが高い |
| 目視で手動塗り | 最も多い。漏れが起きる | rm の中心価値は「確認済みチェック」まで含むこと |

### 2-3. ポジショニング

「モザイクツール」市場ではなく、**「公開前チェック」市場**に置く。

| | 手動で隠す（モザル・Canva・バナー工房） | 自動で検出する |
|---|---|---|
| **写真（顔・ナンバー）** | 競合が非常に強い。rm が正面から戦う場所ではない | Mozaiku・facepixelizer・フォト消しプライバシー |
| **スクショ（API キー・パス・端末情報）** | **空白地帯** | **rm のみ** |

- 勝ち筋は「写真のモザイク」ではなく **「エンジニアが記事・Issue・資料に貼るスクショのマスキング」**。
- 写真向けは「スマホで撮った写真に、PC でまとめて処理したい」という**補助的な入口**として持つ。

### 2-4. 競合から学ぶ（機能ではなく作りから）

1. **モザル**: 1 ページに「使い方・FAQ・他サービスとの違い・対応形式・更新履歴・スマホ可否」を全部入れ、`SoftwareApplication` と `FAQPage` の構造化データを実装している。→ rm に足りないのは機能ではなく **言語化とページ**。
2. **Mozaiku**: タイトルに「顔・ナンバー自動検出」を入れている。→ rm のタイトルは「rm —」で始まり、**検索語が入っていない**。
3. **ソースネクスト**: 「隠す作業から、確認する作業へ」と課題を言語化し、「ローカル処理」「元画像を残す」「AI は完全ではないので目視」と**信頼の担保**を並べている。→ rm も同じ 3 点を持っているのに、サイトでは語っていない。

## 3. 現状診断（2026-11-14 実測）

| # | 症状 | 影響 | 根拠 |
|---|---|---|---|
| 1 | `/robots.txt` と `/sitemap.xml` が **index.html を 200 で返す** | クローラが robots / sitemap を読めない。存在しない URL も 200（ソフト 404） | `curl -sI` で `content-type: text/html` / 13177 bytes。原因は `template.yaml` の `CustomErrorResponses`（403/404 → 200 + index.html） |
| 2 | **`h1` が存在しない**（見出しは `h2` のみ） | ページの主題を機械が判断しにくい | `index.html` に `h1` なし |
| 3 | **構造化データがゼロ** | AI 検索・リッチリザルトで不利 | `application/ld+json` なし |
| 4 | **`canonical` なし / `og:image:alt` のみ** | 正規 URL の明示なし（1 ページなので致命的ではない） | `index.html` |
| 5 | **本文が UI ラベルだけ**（説明文が薄い） | 「何のツールか」を本文から読めない。AI が引用する材料がない | 本文は「自動検出」「書き出し」「プライバシー」の各パネルのみ |
| 6 | **title がブランド先頭**「rm — 写真の顔・ナンバー・秘密をブラウザで隠す」 | 検索語の一致度が弱い。`rm` は Unix コマンドと衝突 | `index.html` |
| 7 | **description に「PC 専用」** | スマホ検索からの流入を自ら捨てている | `index.html` |
| 8 | **インデックス可能ページが 1** | クエリ 1 つ分しか取れない | サイト構成 |
| 9 | **GitHub README の古い版が検索結果に出る**（Gemini 連携の記述が残存） | AI が古い仕様を学習・引用する | 検索結果のスニペットに「Google Gemini または自分の Ollama」 |
| 10 | **名称 `rm` が検索できない** | 「rm とは」は Unix コマンドの解説が返る。指名検索・エンティティ解決が不可能 | — |

## 4. SEO 施策

### P0 — 今週中（合計 半日〜1 日）

**4-1. robots.txt / sitemap.xml を実ファイルにする**

- `public/robots.txt` と `public/sitemap.xml` を追加（S3 の実オブジェクトとして配信される）。
- `template.yaml` の `CustomErrorResponses` から **404 → 200 の書き換えを削除**（403 も同様）。SPA のルーティングをしていないので、フォールバックは不要。
- `scripts/deploy.sh` で 2 ファイルだけ `--content-type` と短い `--cache-control` を明示（現状の `s3 sync` は 1 年 immutable になる）。

```txt
# robots.txt
User-agent: *
Allow: /
Disallow: /test-image-secret/

# AI 検索系クローラ（明示許可。既定でも許可だが意図を示す）
User-agent: GPTBot
Allow: /
User-agent: OAI-SearchBot
Allow: /
User-agent: ChatGPT-User
Allow: /
User-agent: PerplexityBot
Allow: /
User-agent: ClaudeBot
Allow: /
User-agent: Claude-SearchBot
Allow: /
User-agent: Google-Extended
Allow: /

Sitemap: https://rm.okamomedia.tokyo/sitemap.xml
```

**4-2. `h1` と説明コンテンツを足す**

`h1` は 1 つ。ビジュアルを崩さないよう、ヘッダー下に**読み上げ可能な 1 行**として置く。

```html
<h1 class="sr-only">写真とスクリーンショットの顔・ナンバープレート・APIキーを、ブラウザ内だけで隠す無料ツール</h1>
```

アプリの下（または「使い方と安全性」の下）に、**ツールの説明を 600〜900 字**置く。
見出しは質問形にする（AI が抜き出しやすい）。

- `h2` 写真の顔やナンバープレートを隠すには
- `h2` スクリーンショットの API キーやパスワードを隠すには
- `h2` 画像はサーバーに送られる？
- `h2` スマホでも使える？
- `h2` EXIF（GPS）は消える？

各節の**冒頭 40〜60 字で結論を言い切る**（後述の LLMO と共通）。

**4-3. title / description を書き換える**

```html
<title>写真・スクショの顔とAPIキーを隠す無料ツール｜rm</title>
<meta name="description" content="写真の顔と、スクショのAPIキー・パスワードを自動検出してモザイク・黒塗り。画像はブラウザの外に出ず、EXIF（GPS）も削除します。ナンバープレートにも対応。">
```

- `rm` を先頭に置かない。`PC 専用` は description から外す（本文とバッジで伝える）。
- OGP も同じ文言に揃える。

**4-4. 構造化データ**

`WebSite` + `Organization` + `SoftwareApplication` + `FAQPage` を 1 つの `@graph` で。

```json
{

        "APIキー・トークン・パスワード・パスの自動検出",

        "EXIF（GPS・撮影日時）の削除",
```

`FAQPage` は、本文に**実際に書いた** Q&A だけを入れる（本文にない Q&A を入れるのはポリシー違反）。

**4-5. Search Console（既存プロパティを使う）**

- `okamomedia.tokyo` のルートで登録済みのプロパティをそのまま使う（追加の認証は不要）。
- **ドメインプロパティ**として登録されていれば `rm.okamomedia.tokyo` も対象。URL プレフィックスのみの場合は rm が含まれないため、ドメインプロパティを追加する。
- そのプロパティに `https://rm.okamomedia.tokyo/sitemap.xml` を送信し、`ページ` レポートで「検出 - インデックス未登録」を監視する。

| パス | 狙うクエリ | 競合 |
|---|---|---|
| `/hide-api-key.html` | スクリーンショット APIキー 隠す / スクショ パスワード モザイク | ほぼゼロ ← **最優先** |

各ページの型（1 ページ 1 問い）:

**4-7. `llms.txt`**（`public/llms.txt`）

- AI 向けの「このサイトは何か／主要ページ／事実」を 1 ファイルにまとめる。**効果は限定的（業界標準ではない）がコストほぼゼロ**。
- 書く内容は「1 文の定義」「主な機能」「処理はブラウザ内」「無料・MIT」「主要 URL」。

**4-8. 外部からの言及を取る**

- Zenn / Qiita / note に「スクショの API キーを公開前に潰す」（rm の実例つき）
- GitHub の README を最新化（Gemini 記述の削除は既に対応済み。**検索結果のキャッシュが更新されるまで待つ**）
- 「無料モザイクツール 6 選」のようなまとめ記事（例: osiblo）へ掲載依頼。**AI 検索はこうした第三者記事を情報源にする**。

## 5. LLMO（AI 検索向け）

### AI が引用する条件

1. **クロールできる**（robots.txt が壊れている／sitemap がない、は減点）
2. **抽出しやすい構造**（結論 → 手順 → 比較 → 注意）
3. **一次情報**（他サイトにない実測値）
4. **エンティティの一貫性**（名称・1 文説明・URL・`sameAs` を全プラットフォームで一致）
5. **第三者の言及**（比較記事・GitHub・技術記事）

### 5-1. 書き方の型（全ページ共通）

```
【結論】写真とスクショの顔・ナンバー・APIキーを、画像を送信せずブラウザ内で隠せる無料ツールです。（45字）
【理由】MediaPipe と Tesseract.js を WebAssembly で動かし、通信は CSP で localhost に制限しています。
【手順】1. … 2. … 3. …
【数字】顔 0.3 秒 / OCR 込み 1 枚 0.5〜2 秒 / 初回 38MB
【注意】自動検出は 100% ではありません。書き出し前に目視確認を促す警告を出します。
```

- **1 見出し 1 問い**。見出しは検索語ではなく**質問文**にする（AI Overviews は質問文に回答を返す）。
- 数字には**条件**を付ける（「14 枚・正解 25 個で再現率 96%」）。条件のない数字は引用されにくく、誤引用の元。

### 5-2. rm が持っている「引用される武器」

README にすでにある実測値は、そのまま公開ページの資産になる。

- 検出精度: 14 枚・正解 25 個で **再現率 96% / 適合率 100%**
- 速度: 顔 0.3 秒、OCR 込み 1 枚 0.5〜2 秒、集合写真 2〜3 秒
- 初回ロード 38MB（顔モデル + OCR）、以後キャッシュ
- EXIF: `before exif=true gps=true` → `after exif=false gps=false`
- 苦手パターン（プレートが長辺の 5% 未満、30° 以上の傾き、等）を**先に書いている**

「できないこと」を書いているページは、AI から**信頼できる情報源**として扱われやすい。

### 5-3. エンティティを固める（`rm` 問題への対処）

`rm` は Unix コマンドと衝突するため、**常に説明的な語とセットで書く**。

- 固定の 1 文: 「rm は、写真とスクリーンショットの個人情報をブラウザ内だけで隠す無料ツールです。」
- 読みを明記: 「rm（アールエム）」
- `sameAs` に GitHub を入れる／GitHub のリポジトリ説明を**同一文言**にする
- 将来、検索・商標の面で名前を強化したいなら「rm マスク」のような**結合商標**を検討（`rm` 単体は識別力が弱く登録が難しい）

### 5-4. 更新の明示

- 各ページに「最終更新: 2026-11-14」を表示
- `README` とサイトの記述が食い違うと AI が古い方を引く（現に Gemini の記述が残っている）。**仕様変更時は両方同時に直す**

### 5-5. 計測

- AI 検索経由の流入は **referrer が `chatgpt.com` / `perplexity.ai` / `google`（AI Overviews は通常の google）** になる。
- CloudFront アクセスログ（S3 出力）で referrer と UA を集計すれば、解析タグなしで効果測定できる。

## 6. 相談① スマホ対応はすべきか

### 結論

**やる。ただし「フル対応」ではなく 2 段階。まず Phase A（1〜2 日）だけ実施する。**

### 理由

1. **いまのモバイル表示は「壊れている」に近い。** `.layout` は `980px` 以下でも 3 カラム（`268px + 1fr + 330px`）のままで、ブレークポイントは `1180px` と `980px` の 2 つしかない。スマホでは編集領域が数 px まで潰れる。
2. **Google はモバイル版でインデックスする。** AI 検索のクローラもモバイル UA が多い。「PC 専用」の宣言は、検索面での評価を自ら下げている。
3. **競合は全員スマホ対応**（モザル・バナー工房・Mozaiku・Canva）。「スマホで使えない」は比較表で必ず不利になる。
4. **ただし需要の中心は PC。** rm の勝ち筋（API キー・ターミナル・パス）は PC の作業。スマホ需要は「顔・ナンバー」＝競合が最も強い領域なので、**フル投資の回収は見込みにくい**。

### Phase A（1〜2 日）: 「スマホでも 1 枚なら使える」レベル

- [ ] ブレークポイント追加（`900px` と `720px`）。1 カラム化し、`サイドバー → エディタ → 右パネル` の順に積む
- [ ] 主要操作を**下部固定バー**へ（写真を追加 / 検出 / 保存）。`Ctrl+V` 依存を外す
- [ ] 右パネルをタブ or `<details>` に畳む（自動検出 / 書き出し / プライバシー）
- [ ] ハンドルとタップ領域を拡大（`Transformer` の `anchorSize`、ボタン最小 44px）
- [ ] `createImageBitmap(blob, { resizeWidth, resizeQuality })` で**デコード時点で縮小**（現状は原寸デコード後に縮小。48MP の写真は 1 枚で 190MB 前後のメモリを使う）
- [ ] OCR は長辺 1280px に制限（スマホのみ）
- [ ] モデル取得（初回 38MB）の前に確認ダイアログ
- [ ] 複数枚選択時は「スマホでは 1 枚ずつの方が安定します」と案内
- [ ] iOS Safari は HEIC をネイティブにデコードできるため、`heic2any` を**モバイルでは使わない**

**受け入れ条件**: iPhone Safari / Android Chrome で「1 枚の写真 → 顔を検出 → 黒塗り → 保存」が最後まで通る。3 枚以上は警告を出して続行可能とする。

### Phase B（必要になったら）: 編集の作り直し

- ピンチズーム / パン（Konva の `stage.scale`）
- 多角形編集のタッチ対応（頂点ハンドルの当たり判定）
- 縦画面用のツールバー再設計
- PWA 化（オフライン起動）

### 表記ルール

**動くようになるまで「スマホ対応」と書かない。** 先に書いて後から実装すると、景品表示法の優良誤認（実際より著しく優良と示す表示）になり得る。

## 7. 相談② 「フォト消しプライバシーを真似した」と言われないために

### 7-1. リスクの正体

| リスク | 現実味 | 効く対策 |
|---|---|---|
| 著作権侵害（ソースコード・画面デザインのコピー） | 低（自前実装。MediaPipe / Tesseract / Konva を使用） | 画面と文言を独自化する |
| 意匠権侵害（GUI の画像デザイン） | 低〜中（登録されていれば争いになる） | レイアウトを似せない。要調査 |
| 商標権侵害（名称・ロゴ） | 低（別名称） | タイトル・広告・ドメインに相手の名称を入れない |
| 不正競争（周知表示の混同・商品形態の模倣） | 低（名称も見た目も別） | 出所の混同を招く表示を一切しない |
| **「パクリだ」と言われる風評** | **中〜高** | **独自実装と非提携の明示・対象の違い・トーン** |

**法的リスクより風評リスクの方が大きい。** 機能・アイデア自体は法で保護されないため、問題になるのは「見た目」「言葉」「態度」。

### 7-2. 実務ルール

**やらないこと**

- `<title>` / `description` / OGP / ドメイン / ロゴ / アプリ内 UI に「フォト消しプライバシー」を出さない
- 相手のスクリーンショット・図・説明文・キャッチコピー（「隠す作業から確認する作業へ」等）を流用しない
- 「互換」「同等」「上位版」「代わり」といった**比較優位の断定**を書かない（根拠を示せない限り景表法リスク）
- 源さんの note 記事の本文・画像を転載しない（引用は最小限 + 出典リンク）

**やること**

- **独自実装である旨と非提携**を `terms.html` に書く（7-3）。サイト上に由来・感想は書かない
- 違いを**機能の多寡ではなく対象の違い**で語る（「開発者のスクショ」vs「写真」）
- 比較表を出すなら、**条件と日付**を明記（「2026-11 時点、当サイト調べ。価格・仕様は変更される場合があります」）
- 相手の名称はサイト上に出さない（検索結果で並ぶこと自体が連想を生む）

### 7-3. サイトに置く文言（`terms.html` 第 6 条）

> 本サービスのプログラムはリポジトリで公開されています。画像の権利は各利用者に帰属します。
> 本サービスは、特定の商用製品の名称・意匠・コードを流用したものではありません。
> 本サービスは、他社の製品・サービスとの提携・後援・監修などの関係はありません。
> 本ページおよび本サービス内に記載のない製品名・会社名は、それぞれの権利者の商標または登録商標です。

- **由来・感想・個人的な経緯はサイトに書かない。** 利用者に必要な情報ではないうえ、検索結果で「〇〇の模倣」という文脈を自分から作ってしまう。
- 由来は `README`（開発者向けの文書）にだけ残す。

### 7-4. 言われたときの対応

1. **事実で返す**（独自実装、非提携、対象の違い）。感情で返さない
2. **違いを示す**（対象・提供形態・価格・処理場所の表）
3. **直すべき点は即直す**（似ている文言・レイアウトがあれば変更し、その旨を書く）
4. 削除依頼が来たら、まず**具体的な箇所**を確認する。根拠のない要求に全面従属する必要はないが、争うより直す方が安い場合が多い

### 7-5. 事前調査（1〜2 時間）

- J-PlatPat で「フォト消しプライバシー」の**商標**を検索（区分 9・42 など）
- 同社の**意匠**（画像を含む意匠）を検索
- **特許**（画像マスキング関連）を検索
- 結果は日付つきで `docs/legal-check.md` に残す（「調べたうえで問題なし」の記録が、後の説明材料になる）

## 8. 前提が変わったときの要注意事項

| 前提 | 崩れたら起きること | そのときの対応 |
|---|---|---|
| 無料・広告なしを続ける | アクセス増が収益にならない。運用コスト（CloudFront / 転送量）だけ増える | 寄付・Pro 版・API 化を検討。広告を入れるなら「プライバシー」の訴求を書き直す |
| アクセス解析を入れない | 流入経路・離脱が見えない | Search Console + CloudFront ログで代替。GA4 を入れる場合は告知と `privacy.html` の更新が必須 |
| PC 専用のまま | モバイル経由の評価・流入を取り逃す | Phase A だけ実施（1〜2 日）。フル対応は需要を見てから |
| 1 ページ構成のまま | クエリ 1 つ分しか取れない。AI が引用する材料がない | 用途別ページを 5 本。まず `/hide-api-key.html` |
| 自動検出の精度が現状並み | 「検出できなかった」の苦情・信用低下 | 苦手パターンを先に明記しておく（現に README にある）。「確認済みチェック」の導線を強める |
| 競合が同等機能を無料で出してくる | 差別化が「対象の違い」だけになる | OSS・検証可能性・開発者向け機能（`.env`、プロンプト、パス）を深掘りする |
| 「フォト消しプライバシー」の名称を文中で使う | 商標・混同の論点が出る | 本文のみに限定し、非提携を明記。タイトル・広告・ドメインには使わない |
| ソースネクストが Web 版・無料版を出す | 立ち位置が直接衝突する | 「開発者のスクショ」特化を前面に。比較ではなく補完の関係として語る |
